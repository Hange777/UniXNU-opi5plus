# M5-15 — The compositor presents at 2560x1440 and the display completes the swap

**Status:** the display path now carries real compositor frames at the native resolution of the monitor,
with the swap completed and the pixels latched by VOP2. The screen still stops after three frames, and the
reason is now the *original family's* missing default surface, not this port's copy path.

**Payload:** `artifacts/m5/payload-display.img`, sha256 `a7d4f164c06b7ee8…`, kernel `e92de1f27cdadd74…`.
**Log:** `logs/display33-uefi.log`, `logs/display33-a.txt` (1868562 bytes, captured 972.7 s, ended on
`copy 3 (status 0`).

## 1. What was added

`tools/wsl/331-patch-xnu-data-mount.py` gained an **exit report** (`sd-exit=1`): `bsd/kern/kern_exit.c` calls
`opi5plus_trace_exit(p, rv)` at the head of `exit_with_reason()`, the single place every process leaves by.
The record cannot be printed from the exiting thread — the console is usually held by a thread waiting for
the card — so it lands in a 192-entry ring (name, pid, `rv`) that the existing `sd-ps` beat thread prints
every 5 s:

```
opi5plus: exit <comm>[<pid>] rv 0x<rv> sig <signal> code <exit code>
```

`W_EXITCODE(code, sig)` puts the exit code in bits 8..15 and the signal number in the low 7 bits, so one
line says which of the two happened. The patch is regenerated by `tools/wsl/334-make-device-xnu-patch.sh`
(which now also checks out `bsd/kern/kern_exit.c`).

## 2. The run

Native mode, as before: `video 0xe6760000+0xe10000 gop map`, `vop-direct: Esmart2 MST 0x1c14 VIR 0x1c1c
VP2 cfg_done 0x48004`, IOMMU paging on.

```
opi5: display t+985s: swap ok 3 rej 0 (reason 0) copy 3 (status 0, 14745600 B, 0 copies) retired 3 gen 3/3
                     frames 0 gop 0/3 timeouts 0 prepare-fail 0
opi5: display t+985s: vop direct (iommu 1, status 00000019 00000019): flips 3, surfaces mapped 2
                     (map failures 0, let go 0, remaps 2, zap timeouts 0), latch mean 9269 us
                     longest 16467 us (0 over 50 ms), copy fallbacks 0, back to boot 0
opi5: display t+985s: prepare calls=3 failures=0 retried=0 max_attempts=0 waited_ms=0 vsync hz=60
                     sent=0 arms=0 idle=0 late=0 start=1 refresh=1
```

Three swaps accepted, three CPU copies of exactly 2560·1440·4 = 14 745 600 bytes **with status 0**, three
retirements, and three VOP2 flips. The latch mean of 9.3 ms with a 16.5 ms worst case is a 60 Hz panel
being fed at roughly a third of its rate — the number to improve later, not to chase now.

This supersedes the `e00002d8` copies of M5-14: `boot_progress_prepare_scanout()` returning 1 was the whole
difference.

## 3. The process table at that moment

`sd-ps` at t+960 lists 103 processes, including `backboardd`, `SpringBoard`, `runningboardd`, `logd`,
`securityd`, `lsd`, `iconservicesagent`, `mediaserverd`, `ReportCrash`. SpringBoard holds pid 27 with
`stat 2` (waiting) and **never exits during the whole run** — the crash loop of M5-14 belonged to the
640x480 boot (no display) and is gone.

## 4. What the exit report showed

The interesting event is a **mass SIGKILL at t≈690**, about 20 daemons in one beat window:

```
opi5: display t+685s … procs 84
opi5plus: exit biomed[103] rv 0x100 sig 0 code 1
opi5plus: exit backboardd[57] rv 0x9 sig 9 code 0
opi5plus: exit identityservicesd[54] rv 0x9 sig 9 code 0
opi5plus: exit cfprefsd[93] rv 0x9 sig 9 code 0
opi5plus: exit containermanagerd[64] rv 0 sig 0 code 0
opi5plus: exit lockdownd[71] rv 0x9 sig 9 code 0
… imagent, sharingd, CommCenter, bluetoothd, locationd, assistantd, seld, dasd, atc, remindd,
  studentd, navd, passd, analyticsd (all sig 9)
```

`rv 0x9` with `sig 9` is SIGKILL: those processes were killed, they did not crash. launchd restarted them
(`backboardd` comes back as pid 104, which is the client that presents at t+985). Nothing in the log names
the killer: no `memorystatus`/jetsam line, no `launchd` shutdown line. Two facts frame it: the Data volume
is at 349 free blocks (1.4 MiB of 64 MiB) in that same window, and `watchdogd` had already exited cleanly.
**Identifying the sender of those SIGKILLs is open** and is the next diagnostic (a `psignal`-side trace of
the killer's `p_comm`).

Ordinary userland noise, for the record: `biomed` exits `code 1` and `bluetoothd` `code 1` repeatedly,
`mobileactivation` dies of SIGTRAP (`rv 0x5`) until launchd throttles it, `fairplayd.A2` exits 0 in a loop.

## 5. Why the picture stops after three frames

```
t+980: IOMFB: default_fb_surface: No Default FB Surface found. Return error
       display c: C2 pid=104 calls=30 fails=18
         s6#0 0 80000003 0 -> 0
         s6#1 1 1        0 -> 0
         s6#2 1 80000000 0 -> e00002d5   (kIOReturnBusy)
         s6#3 2 80000001 0 -> 0
         s6#4 2 80000000 0 -> e00002d5
```

backboardd's external-method selector 6 is the presentation call; the arguments are (index, surface, 0).
The surface ids that work are `1`, `0x80000001`, `0x80000003`; **`0x80000000` always comes back
`kIOReturnBusy`**, and `default_fb_surface` refuses with the message above. No client ever enables vsync
notification (`arms=0`), so this port's 60 Hz tick never runs — the compositor is not waiting on our vsync.

That is the same end state the official reference records: *"A captured 300-second boot completed three
swaps without a kernel panic and displayed the Apple logo. Home-screen startup remains unverified; capture
the display-server and SpringBoard wait chains…"* This port is now at that parity point at 2560x1440
instead of 640x480, and the remaining piece is the one the same page names: the adapter must supply the
default surface **through the original IOSurfaceRoot factory**, because "the family's
`create_default_fb_surface()` slot returns void; its residual return register is not an object pointer".

## 6. Also still true, and now the top non-graphics blocker

The Data volume is a 64 MiB APFS container in RAM and it is **full** from about t+500:

```
fs_tx_enter_internal: disk3s1 logd_helper: ENOSPC: ttype INSERT num_blocks 1089 free_blocks 978 …
apfs_lowdisk_check_volume: disk3s1 sending lowdisk notification: 8192 …
```

`free_blocks` cycles between 349 and ~1000 of 16 384. Every daemon that writes (`logd`, `cfprefsd`,
`containermanagerd`, `ReportCrash`) is working against a full disk. The seed cannot simply be made larger:
the APFS container size is fixed inside the image (`mkapfs` in `tools/wsl/tmp-make-seed64.sh`), so shipping
a bigger seed in the payload would add unused bytes, not space. The ways out are a Data window on the SD
card (a several-GiB `mkapfs` image written next to the root windows and published by `NativeSd`), or
cutting what the guest writes.

## 7. Reproduce

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\cycle.ps1 -Tag display33 -MaxSecs 1000
```

with `tools/wsl/tmp-payload-display.sh` carrying `--kernel-arg sd-exit=1`; the kernel must be built from
the regenerated `patches/xnu/0002-mount-data-volume.patch`.
